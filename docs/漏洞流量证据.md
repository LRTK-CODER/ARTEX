# 취약점의 여러 트래픽 증거

취약점 상세의 '관련 트래픽'은 페이지를 넘나드는 다중 선택, 용도와 설명, 순서 바꾸기, 연결 해제를 지원한다. 트래픽 화면에서도 기록을 여러 개 골라 기존 취약점 하나에 한 번에 연결할 수 있다. 작업이 이어받은 취약점 증거는 읽기 전용이고, 고치려면 출처 작업으로 들어가야 한다.

시스템 설정의 '에이전트의 트래픽 자동 연결'은 기본값 꺼짐이다. 읽고 바꾸는 API는 `/api/settings`의 `agent_traffic_binding`이다. 켜면 요청·응답 조회, 도구 호출, 프롬프트 때문에 토큰 소비가 늘어난다. 다음 턴의 에이전트부터 새 설정을 쓴다. 끄면 자동 연결 파라미터와 추가 연결 도구를 숨기고, 자동 연결 안내를 넣지 않으며, 이미 실행 중인 세션이 새로 보내는 자동 연결을 거부한다. 수동 연결, 트래픽 캡처, 저장된 증거 읽기와 내보내기는 영향을 받지 않는다.

켜면 기본 흐름은 '발견 사항 저장 → 보고서 에이전트 자동 실행 → 트래픽 확인·연결 → 최신 증거 버전으로 보고서 작성'이다. 보고하는 쪽은 `evidence`에 검증 명령, 핵심 출력, 이미 있는 실제 트래픽 ID와 용도를 남긴다. 보고서 에이전트는 취약점 상세와 실행 기록을 함께 보고 `traffic_search` / `traffic_get`으로 확인한 뒤 `bind_finding_traffic`을 호출하고, 최신 `version`을 읽어 보고서를 저장한다. 스위치를 끄면 보고서 에이전트는 원본 트래픽 검색·읽기 도구를 따로 받지 않고 자동 연결도 하지 않는다. 수동으로 연결한 스냅숏은 여전히 읽어 보고서를 만들 수 있다.

기존 호출자와 호환된다: `report_finding`의 `traffic_refs` / `evidence_hint_id`로 여전히 명시적으로 바로 연결할 수 있다. 연결은 선택이다. TCP처럼 HTTP가 아닌 취약점이거나, 수집하지 않았거나, 정확한 기록을 찾지 못했으면 참조를 생략해도 정상적으로 보고하고 보고서를 쓸 수 있다. 명령 출력, 로그 같은 다른 검증 가능한 증거는 남기고, 연결하지 않은 이유를 적기를 권한다. 필수 필드는 새로 만들지 않는다. 보낸 ID는 모두 올바르고 본문이 완전해야 한다. 하나라도 실패하면 이번 연결 작업 전체를 롤백한다. 보고와 함께 명시적으로 연결하다 실패하면 보고 전체를 롤백한다. 같은 스냅숏을 다시 추가해도 연결이 늘지 않고 설명도 덮어쓰지 않는다.

## 에이전트 번호와 보고서 버전

`report_finding`에 선택 파라미터를 더했다. 배열 순서가 처음 증거 순서다:

```json
{
  "traffic_refs": [
    {"traffic_id": "실제 트래픽 ID", "role": "baseline", "note": "정상 계정 요청"},
    {"traffic_id": "다른 실제 트래픽 ID", "role": "proof", "note": "재현 요청"}
  ]
}
```

용도는 `baseline`(정상 대조), `proof`(취약점 증명), `verification`(추가 검증), `supporting`(보조 증거, 기본값)이다. 먼저 `traffic_search` / `traffic_get`으로 실제 기록을 확인한다. 도메인과 시간은 후보를 거르는 데만 쓰고, 이것으로 작업 소속을 추정하지 않는다.

프롬프트는 [CyberStrikeAI의 취약점 보고 도구 안내](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)를 참고하고 이 프로젝트의 선택적 연결 규칙과 합쳤다. 패킷이 없는 이유를 필수로 검사하는 규칙은 들이지 않는다. ID를 추측하면 안 되고, 패킷을 채우려고 탐지를 되풀이해서도 안 된다.

응답 첫 줄은 그대로 `finding recorded: <탐색 노드 ID>`다. 이어지는 JSON에 독립 취약점 기록 `finding_id`, 탐색 노드 `finding_node_id`, 연결 요약이 있다.

- `get_finding_traffic(finding_id)`는 **독립 취약점 기록 ID**를 쓰고, 순서가 있는 목록과 `version`을 돌려준다. `binding_id`, `side=request|response`, `offset`, `length`를 주면 나눠 읽을 수 있고, 한 조각은 최대 8192바이트다.
- `update_finding_report`의 `finding_id`는 **계속 탐색 노드 ID를 쓴다**. 새 `evidence_version`에는 실제로 읽은 버전을 넣는다. 생성하는 동안 증거가 바뀌면 이전 버전 쓰기를 거부하므로 다시 읽고 다시 만들어야 한다.
- 이전 방식의 보고서 호출이 버전을 넘기지 않으면 기존 트래픽 증거를 다룬다고 주장하지 않는다. 연결, 설명, 용도, 순서가 바뀌면 기존 보고서에 갱신이 필요하다고 표시한다.

자동 연결을 켜면 `add_hint` / `add_task_hint`는 단건 힌트나 일괄 `hints`의 각 요소에 `traffic_refs`를 저장할 수 있다. 플래너가 대신 보고할 때는 `evidence_hint_id`를 넘겨 이 작업의 해당 힌트에 든 참조를 명시적으로 고를 수 있고, 이어받은 힌트는 참조할 수 없다. 시스템은 도메인, 시간, 탐색 기록으로 연결을 추측하지 않는다. 제출에 실패하면 일부만 만든 취약점을 남기거나 보고서를 미리 실행하지 않는다.

기존 취약점에 연결을 빠뜨렸으면 `bind_finding_traffic(finding_id, traffic_refs)`로 추가 연결할 수 있고, 다시 등록할 필요는 없다. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail`은 `finding_id`와 `finding_node_id`를 분명히 돌려준다. 이전 `id`는 탐색 노드라는 뜻을 유지한다.

시작할 때 이전 도구 schema에는 선택 속성만 더하고, 원래 기본 트래픽 도구 연결을 보고서 에이전트까지 넓힌다. 추가 연결 도구는 기본으로 보고서 에이전트에 준다. 사용자 지정 연결 목록, 프롬프트, 설명, 사용 상태는 유지한다. 안내는 최종 도구 조립 뒤에 한꺼번에 더한다: 보고하는 역할은 이미 있는 증거를 넘기고, 보고서 에이전트는 확인·연결·보고서 작성을 맡는다. 플랫폼 대화에 작업 컨텍스트가 없으면 구조화된 힌트로 작업 에이전트에 넘기고 직접 보고하지 않는다. 작업 완료를 판정하기 전에 이미 있는 증거를 먼저 넘긴다. 패킷이 없다고 기다리게 하지는 않는다. 실패한 `report_finding`은 보고서 에이전트를 실행하지 않는다.

## API

기본 경로: `/api/exploration/findings/{finding_id}/traffic`. 독립 취약점 ID를 쓴다. 기존 인증을 그대로 쓰고, `context_task`로 작업 공개 여부와 이어받은 읽기 전용 여부를 검사한다.

| 메서드 / 상대 경로 | 요청 / 응답 |
| --- | --- |
| `GET` | 순서가 있는 요약, 증거 버전, 보고서가 반영한 버전 |
| `POST` | `{"traffic_refs":[...]}` 전체를 한 번에 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"설명"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`. 전체 목록이어야 한다 |
| `GET /{binding_id}` | 스냅숏 메타데이터와 크기가 제한된 본문 미리 보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`. `download=1`이면 원래 바이트 전체를 다운로드 |

버전·순서 집합 충돌이나 보관 중 쓰기는 `409`, 이어받은 데이터에 쓰기는 `403`, 없거나 그 취약점에 속하지 않는 연결은 `404`를 돌려준다. 트래픽·첨부 파일 읽기와 검사에 실패하면 오류를 분명히 돌려준다.

## 저장과 마이그레이션

시작할 때 PostgreSQL을 멱등하게 마이그레이션한다: `traffic_evidence_snapshots`, `finding_traffic_bindings`와 `findings.evidence_version` / `report_evidence_version`(기본값 0)을 더한다. 이전 기록의 글로 연결을 추측해 채우지 않는다.

스냅숏은 원래 트래픽 ID, 수집 시각, URL, 메서드, 상태, 요청·응답 헤더, 본문 길이, SHA-256을 저장한다. 본문은 해시로 `<data>/evidence/blobs/<앞 두 글자>/<hash>.bin`에 저장하고, 정리될 수 있는 `data/traffic`과 따로 둔다. 여러 취약점이 스냅숏·본문을 함께 쓸 수 있다. 스냅숏에는 내용 수정 API가 없고, 검사 값이 맞지 않으면 읽기와 내보내기가 실패한다.

원래 트래픽의 쓰기 잠금을 잡은 채 큰 본문 blob과 이전 디렉터리의 기록까지 포함해 본문 전체를 읽는다. 파일을 먼저 저장하고 검사한 다음, PostgreSQL 트랜잭션 하나로 탐색 노드, 의도 관계, 취약점, 스냅숏, 연결을 쓴다. 커밋한 뒤에야 플래너에 알린다. 실패하면 참조가 없는 파일이 남을 수 있지만 일부만 만든 업무 기록은 생기지 않는다.

PostgreSQL advisory lock `7337741004`가 증거 파일과 SQL 참조를 조정한다. 작업 행 잠금은 보관 대기에 들어간 뒤의 증거 수정을 막는다. 복원은 본문 설치부터 메타데이터 커밋까지 내내 증거 잠금을 유지한다. 취약점을 지우면 연쇄 삭제로 연결도 지워진다.

정리기는 한 시간마다 돌고, 참조가 없고 진행 중인 작업에 쓰이지 않는 내용만 최소 24시간이 지난 뒤 회수한다. 일반 트래픽 정리는 증거 디렉터리를 건드리지 않는다. 핫 데이터를 백업할 때는 PostgreSQL과 `data/evidence`를 함께 백업한다.

## 내보내기와 보관

Markdown에는 순서가 있는 증거 목록과 버전이, JSON에는 메타데이터가 들어간다. CSV에는 개수와 연결 ID가 더해진다. `md-zip`은 취약점 Markdown을 유지하고 다음을 함께 담는다:

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown은 상대 링크로 메시지를 참조한다. 다운로드를 보내기 전에 첨부 파일 복사, 해시 검사, 압축, 디스크 동기화, 모든 ZIP 항목의 CRC 읽기 검사를 마친다. 빠지거나 손상된 것이 있으면 다운로드 전체가 실패한다. 전체 첨부 파일은 바이너리 원래 바이트를 유지한다.

보관 v3는 취약점 연결 관계를 따라 스냅숏과 본문을 모으고, 원래 트래픽이나 도메인에 기대지 않는다. 묶음 검사가 끝난 뒤에야 핫 데이터를 정리하고, 함께 쓰는 증거는 계속 남긴다. 복원은 본문을 먼저 검사해 설치하고, 그다음 트랜잭션으로 메타데이터와 연결을 복원하며, 실패하면 다시 시도할 수 있다. v1/v2도 계속 복원할 수 있고, 빠진 새 필드는 명시적으로 0으로 채운다.

## 검증과 한계

테스트 패키지마다 새로 만든 별도 PostgreSQL 테스트 DB를 `ARTEX_PG_DSN`으로 지정한다. 남아 있는 작업·모델 픽스처가 백그라운드 실행을 일으키지 않게 하기 위해서다. 관련 패키지 테스트를 모두 돌리고, 설정이 없어 건너뛴 테스트가 없는지 확인한다:

```sh
# 패키지마다 실행 전에 ARTEX_PG_DSN을 해당 별도 테스트 DB로 정한다. 명시한 설정이 실패하면 반드시 오류가 나야 한다.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

프런트엔드 검증은 `npx tsc --noEmit`, 영향받은 파일의 Biome 검사, Webpack 빌드, `NEXT_EXPORT=1` 정적 export다. 실행 중인 개발 서버를 덮어쓰지 않도록 별도 캐시 디렉터리를 쓴다.

이 컴퓨터에서 한 종단 간 인수 확인은 별도 포트, 통제된 HTTP / 도메인 HTTPS 대상, 임시 데이터 디렉터리를 썼다. 두 연결 진입점, 페이지를 넘나드는 선택, 순서·설명, 오류 안내, 이어받은 데이터의 읽기 전용, 다운로드, 그리고 원래 트래픽을 지운 뒤의 내보내기, 보관, 핫 데이터 본문 회수, 복원과 해시 검사를 다뤘다.

첫 버전은 전역 증거 조정 잠금을 쓴다. 대량 연결·내보내기나 느린 첨부 파일 다운로드 중에는 다른 증거 작업이 기다릴 수 있다. 기록이나 전체 본문이 없으면 증거를 만들어 채울 수 없다. 이 기능은 캡처 스위치를 바꾸지 않고, HTTPS로 IP에 바로 접속할 때의 인증서 문제도 다루지 않는다.
