# 테스트 규칙

테스트를 쓰거나 고칠 때 따른다. 테스트 대역은 `architecture.md`의 "인터페이스와 다형성"·"의존성 주입", 검사 우회 금지는 `orchestration.md`의 "워커가 지킬 것", 증거 제출은 `issues.md`의 "PR"을 따르고 여기서 되풀이하지 않는다. 제품 코드가 테스트를 알아채지 않는 규칙은 `go-style.md`의 "테스트와 제품 코드"에 있다.

Go는 표준 `testing`만 쓴다. testify·gomock 같은 프레임워크를 들이지 않는다(새 의존성은 `orchestration.md` "누가 정하나").

## 크기와 기본 실행

- 단위 테스트는 한 프로세스에서 외부 도구·LLM·네트워크·실제 DB·sleep 없이 돈다.
- 파일은 `t.TempDir()`에만 쓴다.
- 동시성·공유 상태가 있는 코드는 `go test -race`로 확인한다.
- 느린·네트워크·실도구·실 LLM·실 DB 테스트는 **빌드 태그가 아니라** 실행 중 `t.Skip`으로 거른다(제품 빌드 태그는 `embedui`뿐이다).
  - 현재는 환경 변수와 연결 실패로 거른다. 실제 DB가 필요한 테스트는 `ARTEX_PG_DSN`이 없거나 DB에 연결하지 못하면 각 테스트가 `t.Skip`·`t.Skipf("postgres unavailable: ...")`로 건너뛴다. 실제 LLM·외부 설정이 필요한 테스트는 전용 환경 변수(예: `ARTEX_REVIEW_LIVE_CONFIG`)가 없으면 건너뛴다.
  - `testing.Short()`를 부르는 테스트는 아직 없다. 그래서 지금은 `go test -short ./...`와 `go test ./...`가 같은 테스트를 돈다.
  - 느린 테스트를 새로 넣을 때는 맨 앞에서 `if testing.Short() { t.Skip("...") }`로 `go test -short`에서 빠지게 한다. 환경이 필요한 테스트는 위처럼 환경 변수나 연결 실패로 거른다. 이유를 `t.Skip` 메시지에 적는다.
- `db`·`agent`·`server`·`evidence`처럼 공유 개발 DB를 쓰는 패키지는 `TestMain`에서 PG advisory lock만 잡아 `go test ./...`가 패키지 간에 겹치지 않게 한다. DB 테스트를 추가할 때 이 패턴을 따른다.
- 끝에서 끝까지 테스트는 최소로 둔다. 비율 수치는 정하지 않는다.

## 무엇을

- 패키지의 공개 동작을 테스트한다. 비공개 함수와 호출 순서는 검증하지 않는다.
- 외부 경계(LLM, SMTP, HTTP, 하위 프로세스) 너머만 가짜로 둔다. 가짜는 그 경계의 좁은 인터페이스(`llm.Provider`, `http.RoundTripper`, `notify.Channel` 등)를 손으로 구현한다.
- 상태 검증(결과 값 확인)을 상호작용 검증(무엇을 불렀는지 확인)보다 우선한다.
- 표를 쓴 테스트(`[]struct{...}`를 `for _, tc := range`로 도는 방식)를 기본으로 한다. 경우마다 `t.Run(tc.name, ...)`로 이름을 붙인다.

## 결정성

- 시계·난수·LLM은 고정값이나 손으로 만든 가짜를 쓴다. 인자로 받는 방법은 `architecture.md`의 "의존성 주입"에 있다.
- 불안정한 테스트를 재실행으로 넘기지 않는다. 시간에 기대지 말고 `context`·채널로 기다린다.

## 대역(가짜)

- 가짜는 테스트 파일 안이나 패키지의 테스트 전용 파일에 손으로 쓴다. 미리 정한 응답을 차례로 돌려주는 것은 괜찮다.
- **가짜를 실제 구현보다 너그럽게 만들지 않는다.** 실제가 거부하는 입력은 가짜도 거부하고, 실제가 올리는 오류는 가짜도 올린다. 가짜를 느슨하게 바꿔 테스트를 통과시키지 않는다.

## 회귀와 기대값

- 버그 수정에는 수정 전에 실패하던 테스트를 넣는다.
- 버그 수정·동작 변경 PR은 두 출력을 PR 검증 섹션에 붙인다. main 사본(`git worktree add /private/tmp/<이름> origin/main`)에 새 테스트 파일(`*_test.go`)만 복사해 돌린 출력(실패, `go test ./<패키지>/ -run <테스트>`)과 PR 브랜치에서 돌린 출력(통과)이다. 끝나면 `git worktree remove /private/tmp/<이름>`으로 사본을 지운다. 새 패키지·새 함수만 추가하는 PR은 제외한다(되돌리면 컴파일 오류로 늘 실패해 알려 주는 것이 없다).
- 기대값을 구현에 맞춰 고치거나, 통과만 노려 하드코딩하지 않는다. 기대값을 바꾸면 예전 기대가 왜 틀렸는지 PR에 적는다.
- 정답 파일(golden file)도 기대값이다. 바꾸면 이유를 PR에 적는다. 생성 방식(예: `-update` 플래그)을 두면 무심코 덮어쓰지 않게 기본은 끈다.

## skip

- `t.Skip`에는 사유를 단다. 두 종류로 나눈다.
  - 환경 거르기: 필요한 환경(DB 연결, 환경 변수, 외부 도구)이 없어 건너뛴다. 사유만 적는다. 예: `t.Skipf("postgres unavailable: %v", err)`.
  - 알려진 실패: 아직 못 고친 결함 때문에 건너뛴다. 사유와 이슈 번호를 단다. 예: `t.Skip("#123 파서가 아직 주석을 읽지 못한다")`.
- Go에는 xfail이 없다. 아직 못 고치는 실패는 테스트를 거짓 통과로 두지 말고, 이슈 번호를 단 `t.Skip`으로 빼거나, 현재 동작을 그대로 검증하고 `// TODO: #<번호>`로 바뀔 것을 적는다.

## 차단 로직과 주입 표본

- 상한·형식 검사 같은 차단 로직에는 걸려야 하는 입력(음성 표본)의 테스트를 하나 이상 둔다.
- 프롬프트 주입 문구를 담은 입력을 고정 표본(예: `testdata/` 아래)으로 둔다. 손으로 만든 가짜 LLM으로 흐름을 돌려, 표본 때문에 흐름(도구 선택, 결과 채택)이 바뀌지 않는지 검증한다.

## 프런트엔드

- 프런트엔드 테스트는 최소다. 순수 로직은 `node --test`로 도는 `web/**/*.test.mjs`로 둔다. 컴포넌트 렌더링 테스트 도구(새 러너)를 들이는 것은 새 의존성이다(`orchestration.md` "누가 정하나").
