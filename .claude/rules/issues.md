# 이슈·PR 규칙

이슈는 PM이 만들고 워커가 읽는다. 워커는 이슈 본문만 보고 일한다. 그래서 이슈는 그것만 읽어도 이해되고, 끝났는지를 명령으로 확인할 수 있어야 한다.

브랜치 이름, 병합 방식과 순서는 `branching.md`를 따른다. PM과 워커의 역할과 보고 절차는 `orchestration.md`를 따른다. 여기서는 되풀이하지 않는다. PR 제목과 본문 형식은 이 문서의 "PR"이 정본이다.

## 템플릿

마크다운 템플릿만 쓴다(`.github/ISSUE_TEMPLATE/*.md`). YAML 이슈 폼은 쓰지 않는다. gh CLI가 YAML 폼을 읽지 못하고, private 저장소에서는 폼의 필수 항목 검사도 동작하지 않는다. 필수 항목은 이 문서와 PM 확인으로 지킨다. `config.yml`(`blank_issues_enabled` 등)은 두지 않는다. 쓰기 권한이 있는 사람과 gh·API 경로에는 효과가 없다.

| 템플릿 | 쓰는 경우 | 필수 섹션 |
|---|---|---|
| `work.md` (작업) | 기능·정리·문서·리팩터링·테스트·CI | 배경과 이유, 완료 기준, 범위 밖, 미결 질문 |
| `bug.md` (버그) | 기대와 다르게 동작하는 것 | 현재 동작, 기대 동작, 재현 절차 + 작업 이슈의 필수 섹션 |
| `research.md` (조사) | 구현 전에 사실 확인·선택지 비교가 필요한 것 | 배경과 이유, 답할 질문, 완료 기준, 범위 밖, 미결 질문 |

"관련 파일과 기존 패턴"은 선택이다. 아는 만큼만 적는다.

조사 템플릿을 따로 두는 이유: 조사의 결과물은 코드가 아니라 보고서라서 완료 기준의 모양이 다르다. 모호한 작업을 구현 이슈에 억지로 넣으면 워커가 추측으로 메운다. 먼저 조사 이슈로 답을 얻고, 그 답으로 구현 이슈를 쓴다.

## 이슈 작성 원칙

1. 팀원에게 설명하듯 배경과 이유를 쓴다. 이 이슈만 읽고 이해돼야 한다.
2. 완료 기준마다 확인 방법(명령, 테스트 이름, 기대 결과)을 붙인다. "잘 동작한다"는 기준이 아니다.
3. 범위 밖을 적는다. 없으면 "없음".
4. 미결 질문이 비어 있지 않으면 구현 워커에게 넘기지 않는다. 모호하거나 보안에 민감하면 조사 이슈로 먼저 나눈다.
5. 짧게 쓴다. 환경·설정 설명은 이슈가 아니라 AGENTS.md와 규칙 문서에 둔다.
6. 내부 약어, 회차 번호, 우선순위 기호(P0, P1 등)를 쓰지 않는다. 말로 풀어 쓴다. 이슈 코멘트, PR, 워커 보고서도 같다.
7. 여러 단계로 된 작업은 확인 지점으로 나누고, 지점마다 결과를 보고하게 한다.

## 작업 크기

- 작업·버그 이슈 하나 = PR 하나 = 몇 시간 분량. 조사 이슈는 PR 없이 보고서로 끝난다.
- PR은 100~200줄을 목표로 한다. 400줄은 권고 상한이다(강제하지 않는다). 줄 수가 적어도 파일이 많이 흩어지면 큰 것이다.
- PR 하나는 Conventional Commits type 하나다. type이 섞이면 나눈다. 리팩터링은 따로 보낸다.
- PR 하나에 변경과 그 테스트를 함께 담는다. 병합 뒤에도 main이 동작해야 한다.

## 분할: 부모 이슈와 sub-issue

큰 작업은 두 단계로 나눈다.

- 부모 이슈 = 기능 하나. 구현 워커에게 직접 넘기지 않는다. 템플릿 없이 아래 골격으로 쓰고, 유형 라벨 하나를 붙인다(미결 질문이 있으면 `needs-decision`도).

      ## 배경과 이유
      ## 단계
      - [ ] #<sub-issue 번호> <한 줄 설명>
      ## 미결 질문

- sub-issue = PR 하나. 작업·버그·조사 템플릿으로 쓴다.
- 셋째 단계는 만들지 않는다. 너무 크면 부모를 나눈다.
- 순서는 의존 관계(blocked by)로 표시한다. 의존이 없는 sub-issue는 병렬로 진행할 수 있다.
- 계층을 나눌 때는 인터페이스를 먼저 병합한다. 병합 순서와 stacked PR은 `branching.md`의 "PR과 병합"에 있다.

## 라벨

라벨 목록, 쓰는 법, 쓰지 않는 라벨은 `.github/labels.md`가 정본이다.

쓰지 않는 기능: Projects, stale 봇, issue types(조직 전용), PR 제목 검사 Action. 마일스톤도 쓰지 않는다. 부모 이슈가 그 역할을 한다.

## 생명주기

1. **만들기.** PM이 템플릿 골격으로 이슈를 만든다. 소유자 승인은 필요 없다. 미결 질문이 있으면 `needs-decision`을 붙인다.
2. **착수.** 미결 질문이 없고 상태 라벨이 없는 이슈만 워커에게 넘긴다.
3. **완료.** 작업·버그 이슈는 PR 본문의 `Closes #N`으로 병합 때 completed로 닫힌다. 조사 이슈는 PR이 없으므로 PM이 보고서 전문을 이슈 코멘트로 올린 뒤 소유자 승인 후 completed로 닫는다.
4. **그 밖의 닫기.** not planned, duplicate는 소유자 승인 후 사유 코멘트와 함께 닫는다.
5. **부모 이슈.** sub-issue가 모두 닫히면 소유자 승인 후 completed로 닫는다.

비활성을 이유로 이슈를 닫지 않는다. PM이 주기적으로 사람의 판단으로 정리한다.

이슈 생성·라벨·닫기 명령은 PM skill(`.claude/skills/pm/SKILL.md`)에 있다.

## PR

- 제목이 squash 뒤 main의 커밋 제목이 된다. Conventional Commits type과 한국어 설명으로 쓴다. 예: `feat: 파서 뼈대를 추가한다`.
- 본문은 `.github/pull_request_template.md`(요약, 검증, `Closes #N`)를 따른다.
- 검증 섹션에는 실제로 실행한 명령과 관찰한 결과만 쓴다. 실행하지 않았으면 "검증 안 함: 이유".
- 닫는 이슈마다 `Closes #N`을 한 줄씩 쓴다. 이슈가 없으면 없는 이유를 한 줄 적는다. 이슈의 일부만 처리하는 PR에는 닫기 키워드를 쓰지 않는다.
- 작성 워커 기록, 자기 리뷰 체크리스트는 본문에 넣지 않는다. 도구가 붙이는 생성 표시 줄은 넣어도 된다.

## 결과 공유 코멘트

PM이 쓰고, 매번 소유자 승인을 받지 않는다. 워커는 코멘트하지 않고 보고서만 쓴다.

- 조사 이슈: 보고서 전문.
- PR: 검증 보고서(재검증 포함), 구현 중 PM·소유자가 답한 설계 선택(질문, 선택지, 답, 이유), 병합 판단(근거와 남긴 지적의 처리 계획). 구현 보고서는 PR 본문과 겹치므로 올리지 않는다.
- 로컬 파일 경로만 적지 않는다. 내용을 올린다.
- 비밀값(API 키, 토큰)과 비공개 분석 대상 원문은 올리지 않는다.
- 한 코멘트 한도(약 65,000자)를 넘으면 여러 코멘트로 나눈다. 명령 출력처럼 긴 부분은 `<details>`로 접는다.

## 리뷰 체크리스트

1. 이슈의 완료 기준을 하나씩 충족하는가. 확인 명령을 다시 실행해 본다. `gh pr checks <번호>`로 CI 통과도 확인한다.
2. 설계가 맞는가. 가장 중요한 항목이다. 기준은 `architecture.md`다.
3. 기능, 복잡도, 테스트(이슈에 적힌 경계 조건 포함)를 본다. 코드가 깨지면 이 테스트가 실제로 실패하는가.
4. 범위 밖 변경이나 섞인 리팩터링이 없는가.
5. 명령·설정·동작을 바꾸는 PR은 같은 PR에서 `AGENTS.md` 명령 절과 해당 규칙 문서를 고쳤는가.
6. 너무 크면 분할을 요청하는 것이 기본 대응이다.
7. 지적은 차단 사항과 `Nit:`(선택 사항)로 나눈다. 정확성이나 요구사항에 영향을 주는 빈틈만 차단 사항이다. 코드가 분명히 나아지면 완벽하지 않아도 "병합해도 된다"로 결론 낸다.

결함은 테스트와 확인 명령이 잡는다. 리뷰는 설계와 이해 가능성에 집중한다.
